Budget math **[inference]**: Spark Hosting = 10 GB storage, 360 MB/day transfer (https://firebase.google.com/pricing). 100 MB of images is 1% of storage. A full download of all images is ~27% of a day's transfer, so precaching all photos is not viable; "cache as viewed" is: ~20 exercises × 2 photos ≈ 2.3 MB per new workout.

| Option | Pros | Cons / facts |
|---|---|---|
| **A. Commit images to our repo** | Simplest build; offline dev; images are just `public/` assets; content is git-addressed | +100 MB in history forever. GitHub: warn > 50 MiB per file, block > 100 MiB; repos "ideally less than 1 GB" (https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-large-files-on-github). Our largest file is 0.9 MB, so fine. Every clone/CI checkout pulls 100 MB unless `fetch-depth: 1` |
| **B. Download at build from a pinned SHA + checksum** | Small repo; dataset upgrade = change one SHA | GitHub tarballs (`codeload…/tar.gz/<sha>`) are **not byte-stable**: "the outer compressed archive may have a different byte layout", extracted contents are stable (https://docs.github.com/en/repositories/working-with-files/using-files/downloading-source-code-archives). So checksum the **extracted tree** (e.g. a committed `sha256` manifest of `exercises/**`), not the tarball. Alternative: `git fetch --depth 1 origin <sha>` — git verifies objects by hash **[inference]**. Build depends on GitHub availability and unauthenticated limits (see C) |
| **C. Hotlink `raw.githubusercontent.com`** | Zero Hosting transfer | Contradicts the spec constraint "catalog and photos shipped as static hosting assets". GitHub tightened limits for unauthenticated "downloading files from raw.githubusercontent.com" (https://github.blog/changelog/2025-05-08-updated-rate-limits-for-unauthenticated-requests/); the number is not published **[unconfirmed]**. AUP: GitHub may "throttle your file hosting" for excessive bandwidth (https://docs.github.com/en/site-policy/acceptable-use-policies/github-acceptable-use-policies, §9). Measured headers: `cache-control: max-age=300`, `access-control-allow-origin: *`, `cross-origin-resource-policy: cross-origin`, `content-type: image/jpeg` |

Recommendation for the owner **[inference]**: A or B. B keeps the repo small but needs a manifest and a fetch step in CI; A has fewer moving parts. Either way, serve from `/exercises/<id>/<n>.jpg` on Hosting with a long `Cache-Control` via `firebase.json` `headers` (https://firebase.google.com/docs/hosting/full-config#headers), and runtime-cache in the SW (§6).

## 2. Firestore offline persistence (JS SDK 13) + TanStack Query v5

Versions: `firebase` 13.2.0, `@tanstack/react-query` 5.107.1 (npm registry).

**API.** `enableIndexedDbPersistence` / `enableMultiTabIndexedDbPersistence`: "This API is now obsolete… will be removed in a future major release. Instead, set `FirestoreSettings.localCache` to an instance of `PersistentLocalCache`" (https://firebase.google.com/docs/reference/js/firestore_.md).

```ts
import { initializeFirestore, persistentLocalCache, persistentMultipleTabManager } from 'firebase/firestore';
export const db = initializeFirestore(app, {
  localCache: persistentLocalCache({ tabManager: persistentMultipleTabManager() /*, cacheSizeBytes */ }),
});
```
- Web persistence is **off by default**; memory cache is the default; `persistentLocalCache` without a tab manager = single-tab (https://firebase.google.com/docs/firestore/manage-data/enable-offline).
- `cacheSizeBytes`: "default value is 40 MB… at least 1 MB… `CACHE_SIZE_UNLIMITED` to disable garbage collection" (https://firebase.google.com/docs/reference/js/firestore_.persistentcachesettings.md).
- Supported only in Chrome, Safari, Firefox (enable-offline page).

**IndexedDB limits** (https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria): Chromium up to 60% of disk per origin; Firefox best-effort min(10% disk, 10 GiB group); Safari ~60% in the browser app, and a Home Screen web app gets the same quota. Safari deletes script-writable storage (incl. IndexedDB, SW caches) after 7 days of Safari use without interaction, but "Web applications added to the home screen are not part of Safari and thus have their own counter of days of use" (https://webkit.org/blog/10218/full-third-party-cookie-blocking-and-more/). `navigator.storage.persist()` is supported since Safari 17 and granted by heuristics such as running as a Home Screen Web App (https://webkit.org/blog/14403/updates-to-storage-policy/). **[inference]** Call `persist()` after sign-in.

**Offline behaviour** (https://firebase.google.com/docs/reference/js/firestore_.md):
- `getDoc`/`getDocs` "attempt to provide up-to-date data… by waiting for data from the server, but may return cached data or fail if you are offline". `getDocFromCache` errors if not cached; `getDocsFromCache` returns empty.
- `onSnapshot`: "Local writes in your app will invoke snapshot listeners immediately" (latency compensation); `metadata.hasPendingWrites` marks unsynced docs; metadata-only events need `{ includeMetadataChanges: true }` (https://firebase.google.com/docs/firestore/query-data/listen). Offline, listeners fire on cache changes; `fromCache: true` = maybe stale (enable-offline page).
- **Writes:** `setDoc`/`updateDoc`/`addDoc`: "the returned Promise does _not_ resolve until the data is successfully written to the remote Firestore backend" (reference above). **[inference]** Never `await` a write in the session UI; fire it, catch errors, and rely on the listener/cache. This matters for "a session must never be blocked".

**TanStack Query v5 combination**
- `networkMode`: `online` (default) pauses queries offline; `always` ignores online state, `refetchOnReconnect` then defaults to `false`; `offlineFirst` runs `queryFn` once then pauses retries (https://tanstack.com/query/latest/docs/framework/react/guides/network-mode).
- `staleTime: Infinity` or `'static'` = never stale; `gcTime` default 5 min (https://tanstack.com/query/latest/docs/framework/react/reference/useQuery).
- `setQueryData` updates must be immutable (https://tanstack.com/query/latest/docs/framework/react/guides/updates-from-mutation-responses).
- No official Firestore recipe exists **[unconfirmed]**. The subscription pattern (socket pushes into the cache, `staleTime: Infinity`) is from the maintainer's blog, linked from the docs' community section (https://tkdodo.eu/blog/using-web-sockets-with-react-query).

Sketch **[inference]**:
```ts
// queryClient defaults: Firestore owns cache/network decisions
new QueryClient({ defaultOptions: {
  queries: { networkMode: 'always', staleTime: Infinity, retry: false, refetchOnWindowFocus: false },
  mutations: { networkMode: 'always' },
}});
// per subscribed key: one onSnapshot pushes into the cache
useEffect(() => onSnapshot(q, s => qc.setQueryData(key, s.docs.map(toModel))), [key]);
useQuery({ queryKey: key, queryFn: () => getDocs(q).then(s => s.docs.map(toModel)) });
// mutation: don't await server ack
useMutation({ mutationFn: async (v) => { void setDoc(ref, v).catch(report); } });
```

## 3. Google sign-in in an installed PWA (Firebase Auth)

From https://firebase.google.com/docs/auth/web/redirect-best-practices:
- Third-party storage blocking breaks the redirect flow on Chrome M115+, Firefox 109+, Safari 16.1+ unless set up.
- Firebase Hosting: on `*.firebaseapp.com` no action needed. On a custom domain or `*.web.app`, **Option 1:** set `authDomain` to the domain that serves the app, add `https://<that-domain>/__/auth/handler` to the OAuth client's redirect URIs, and keep `/__/firebase/init.json` current (redeploy).
- Option 2: `signInWithPopup` ("popups are occasionally blocked… less smooth on mobile"). Options 3–5: reverse proxy, self-hosted helper files, provider SDK + `signInWithCredential`.
- Firebase Hosting reserves `/__` (https://firebase.google.com/docs/hosting/reserved-urls), so the handler is served on our origin with no extra work. The SW must not serve the app shell for these paths (§6).

**iOS standalone and Android Chrome:** no official Firebase statement on popup vs redirect in iOS standalone mode **[unconfirmed]**. Community reports show popups in iOS standalone opening a separate Safari context and redirect issues before the third-party-storage fix (https://github.com/firebase/firebase-js-sdk/issues/77, https://github.com/firebase/firebase-js-sdk/issues/3115). **[inference]** With `authDomain` = our own origin, `signInWithRedirect` stays first-party and is the safer default for installed PWAs on both platforms. Keep popup for desktop if wanted. Verify on a real iPhone (installed) and an Android device before choosing.

**Auth emulator in Playwright** (https://firebase.google.com/docs/emulator-suite/connect_auth):
- `connectAuthEmulator(auth, 'http://127.0.0.1:9099')`.
- Popup/redirect against the emulator open a local fake sign-in page that creates mock accounts; tests can click it.
- Non-interactive: `signInWithCredential(auth, GoogleAuthProvider.credential('{"sub":"abc123","email":"foo@example.com","email_verified":true}'))`; `sub` picks the user.
- Reset: `DELETE http://127.0.0.1:9099/emulator/v1/projects/{projectId}/accounts` (https://firebase.google.com/docs/reference/rest/auth).

Sketch **[inference]**: expose a test-only hook (behind `import.meta.env.MODE === 'test'`) that calls `signInWithCredential` with a fake token, invoked from `page.evaluate`; or drive the emulator's fake popup page once for an E2E of the real button.

```ts
let lock: WakeLockSentinel | null = null;
async function acquire() { try { lock = await navigator.wakeLock?.request('screen') ?? null; } catch { lock = null; } }
document.addEventListener('visibilitychange', () => {
  if (sessionActive && document.visibilityState === 'visible') void acquire();
});
// release: await lock?.release(); lock = null;
```
(Pattern from the MDN page above.) Request may reject (low battery, policy), so feature-detect and never block the session on it **[inference]**.

## 5. Short generated sounds on iOS (Web Audio)

- Autoplay policy: "Create or resume context from inside a user gesture"; a context created outside a gesture starts `suspended` and needs `resume()` (https://developer.mozilla.org/en-US/docs/Web/API/Web_Audio_API/Best_practices).
- iOS: "when a user leaves the page (e.g., switches tabs, minimizes the browser, or turns off the screen) the audio context's state changes to `interrupted` and needs to be resumed" (https://developer.mozilla.org/en-US/docs/Web/API/BaseAudioContext/state). So **no sounds while backgrounded or locked**; timers in a hidden page also cannot be relied on **[inference]**. The rest-timer sound only works with the screen on, which is why the Wake Lock matters.
- `navigator.audioSession.type` (`'playback' | 'transient' | 'ambient' | …`): Safari 16.4+ only, not Chrome, Firefox preview (https://github.com/mdn/browser-compat-data/blob/main/api/AudioSession.json, https://developer.mozilla.org/en-US/docs/Web/API/AudioSession). Web Audio on iOS follows the silent switch by default; `'playback'` is reported to bypass it but interrupts other apps' audio (e.g. the user's music) **[unconfirmed; bug reports only]** (https://bugs.webkit.org/show_bug.cgi?id=252746). **[inference]** Use `'transient'` or leave default so music keeps playing, and add a vibration fallback where supported (not on iOS).

```ts
const ctx = new AudioContext();               // create lazily
async function unlock() { if (ctx.state !== 'running') await ctx.resume(); }  // call in "Start workout" tap handler
function beep(freq = 880, ms = 150) {
  if (ctx.state !== 'running') return;        // suspended/interrupted: skip, never throw
  const o = ctx.createOscillator(), g = ctx.createGain();
  o.frequency.value = freq; g.gain.setValueAtTime(0.2, ctx.currentTime);
  g.gain.exponentialRampToValueAtTime(0.001, ctx.currentTime + ms / 1000);
  o.connect(g).connect(ctx.destination); o.start(); o.stop(ctx.currentTime + ms / 1000);
}
document.addEventListener('visibilitychange', () => { if (document.visibilityState === 'visible') void unlock(); });
```
Resuming on `visibilitychange` without a gesture may still be refused on iOS **[unconfirmed]**. Re-unlock on the next tap.

## 8. Firestore rules for `/users/{uid}/**`

Canonical rule, from "allow read, update, delete: if request.auth != null && request.auth.uid == userId;" (https://firebase.google.com/docs/firestore/security/rules-conditions). With `rules_version = '2'`, `{document=**}` matches **zero** or more segments (v1: one or more), and access is granted if **any** matching rule allows it (https://firebase.google.com/docs/firestore/security/rules-structure). So a broad `/users/{uid}/{document=**}` allow overrides narrower validation; validate in per-collection matches instead **[inference from the any-match rule]**.

Validation tools (https://firebase.google.com/docs/firestore/security/rules-fields): `keys().hasAll([...])`, `keys().hasOnly([...])`, `diff(resource.data).affectedKeys().hasOnly([...])`, `is string|int|float|number|bool|timestamp|list|map|…`. `size()` on strings counts characters (https://firebase.google.com/docs/reference/rules/rules.String); lists/maps have `size()` too. **No rules function returns total document bytes** (not in the reference; doc max is 1 MiB, depth 20: https://firebase.google.com/docs/firestore/quotas). Bound size via key allowlists plus per-field `size()` caps. Rules limits: 10 `get/exists` per single-doc request, 20 for batches, 1,000 expressions per request, 256 KB ruleset source (rules-structure).

```
rules_version = '2';
service cloud.firestore {
  match /databases/{db}/documents {
    function isOwner(uid) { return request.auth != null && request.auth.uid == uid; }
    match /users/{uid} {
      allow read, delete: if isOwner(uid);
      allow create, update: if isOwner(uid) && validProfile(request.resource.data);
      match /workouts/{id} {
        allow read, delete: if isOwner(uid);
        allow create, update: if isOwner(uid) && validWorkout(request.resource.data);
      }
      // one match per subcollection; no catch-all write rule
    }
    function validWorkout(d) {
      return d.keys().hasOnly(['startedAt','finishedAt','sets','note'])
        && d.startedAt is timestamp
        && d.sets is list && d.sets.size() <= 200
        && (!('note' in d) || (d.note is string && d.note.size() <= 2000));
    }
  }
}
```

**Tests** (`@firebase/rules-unit-testing` 6.0.0: peer `firebase ^13`, `engines.node >=24.12.0`, https://registry.npmjs.org/@firebase/rules-unit-testing). API: `initializeTestEnvironment`, `authenticatedContext(uid)`, `unauthenticatedContext()`, `withSecurityRulesDisabled`, `assertSucceeds`/`assertFails`, `clearFirestore`, `cleanup` (https://firebase.google.com/docs/rules/unit-tests). Host/port can be omitted: discovered via `FIRESTORE_EMULATOR_HOST` or `FIREBASE_EMULATOR_HUB` (typings in the 6.0.0 tarball), and `firebase emulators:exec` exports both (https://github.com/firebase/firebase-tools/blob/main/src/emulator/env.ts). ## 10. Steiger 0.10 + @feature-sliced/steiger-plugin 0.8.2 and FSD v2.1

From the 0.8.2 tarball (`dist/index.js`) and the steiger README (https://github.com/feature-sliced/steiger):
- **`recommended` enables (all at `error`):** ambiguous-slice-names, excessive-slicing (hard-coded 20 slices per layer/group), forbidden-imports, inconsistent-naming, insignificant-slice, no-layer-public-api, no-public-api-sidestep, no-reserved-folder-names, no-segmentless-slices, no-segments-on-sliced-layers, no-ui-in-app, public-api, repetitive-naming, segments-by-purpose, shared-lib-grouping (hard-coded 15), typo-in-layer-name, no-processes.
- **Off in recommended:** no-cross-imports, no-higher-level-imports (both covered by forbidden-imports), import-locality, no-wildcard-exports.
- Severity: `'off' | 'warn' | 'error'` or `[severity, options]` (`dist/app.d.ts`). The thresholds above are constants, not options **[inference from dist]**. CLI: `--watch`, `--fail-on-warnings`, `--ignore-warnings`, `-c`.

```ts
// steiger.config.ts
import { defineConfig } from 'steiger';
import fsd from '@feature-sliced/steiger-plugin';
export default defineConfig([
  ...fsd.configs.recommended,
  { ignores: ['**/__mocks__/**', '**/*.test.*'] },
  { files: ['./src/shared/**'], rules: { 'fsd/public-api': 'off' } },
  { rules: { 'fsd/insignificant-slice': 'warn', 'fsd/no-wildcard-exports': 'error' } },
]);
```

**FSD v2.1:**
- "The main change in v2.1 is the new mental model… pages first": keep most UI and logic in the page; move it down only when several pages reuse it. Steiger's `insignificant-slice` flags entities/features used by one page (https://feature-sliced.design/docs/guides/migration/from-v2-0).
- **Widgets:** "large self-sufficient blocks of UI", "most useful when they are reused across multiple pages"; a big block used on one page "should not be a widget" (https://feature-sliced.design/docs/reference/layers).
- **App:** app-wide matters such as context providers; segments `routes` (router configuration), `store`, `styles`; usually no slices (same page). The React Query guide places the provider at `src/app/providers/query-provider.tsx` (https://feature-sliced.design/docs/guides/tech/with-react-query).
- **Data access:** `shared/api` holds "the API client and potentially also functions to make requests to specific backend endpoints"; slice-specific requests go in that slice's `api` segment; "Avoid placing API calls and response types in the `entities` layer prematurely" (https://feature-sliced.design/docs/guides/examples/api-requests). Query keys/`queryOptions` in `shared/api` or `entities/*/api`; mutations "in the api segment near the place of use" or in shared/entities via `mutationFn` (react-query guide).
- **[inference]** Mapping: Firebase init, `db`/`auth` instances and the Firestore converters → `shared/api` (or `shared/firebase`); per-page queries → `pages/<p>/api`; reused ones (workouts, sets) → `entities/<e>/api`; router + `QueryClientProvider` + auth gate → `app`.
