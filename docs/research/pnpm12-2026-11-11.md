**Limitations / gaps vs 11** (from the two blog posts unless noted):
- `pnpm install --resolution-only` is removed; use `pnpm peers check`.
- `--frozen-lockfile false` (boolean flag with a separate value) is rejected; use `--no-frozen-lockfile`.
- pnpmfile `importPackage` hook not run; `filterLog` ignored with a warning (DOCS `migration-v11.md`).
- Command shims for other package managers are never created automatically (`pnpm shim add`).
- Private SSH Git deps need a machine-level `git config url.….insteadOf`.
- Distribution: "Homebrew, winget, Scoop, and Chocolatey don't offer it yet." The posts also say npm `latest` still points to 11, but **that is outdated**: `latest` is 12.18.0 today (REG).
- Experimental parts: `remoteSideEffectsCache` ("opt-in proof of concept", restore on Linux glibc only), `lockfile.format: v13` (12.19.0).
- WebContainers cannot run the native binary; they need `@pnpm/wasm` (DOCS `installation.md`).
- No list of features of 11 missing from 12 is published; the blog says 12 keeps 11's commands, flags and settings. **[unconfirmed]** that nothing else is missing.

**Release-age clash today:** under the owner's `minimumReleaseAge: 10080`, **12.18.0 is too young until 2026-11-12 00:56 UTC**. **12.17.0** (2026-10-30 14:23 UTC) is the newest version past 7 days (REG). [inference]

## 2. Install and pin

### Pin fields (package.json)

| Field | Behaviour in 12 | Source |
|---|---|---|
| `devEngines.packageManager` `{name, version, onFail}` | Accepts exact or range. Resolved version stored in `pnpm-lock.yaml` under `packageManagerDependencies`. When the lockfile has none, pnpm records the running pnpm only if it is older than `minimumReleaseAge`; otherwise it records the newest version in range that is (12.9.0). | DOCS `package_json.md`; CL 12.9.0 |
| `packageManager: "pnpm@x.y.z"` | Exact only. For pnpm 12 its resolution is also written to the lockfile, as a leading "boot document" | DOCS `package_json.md` |
| `trustPolicy: no-downgrade` | Also checks the pinned pnpm version before switching to it | DOCS `settings/dependency-resolution.md#trustpolicy` |
| `pmOnFail` | `download` (default) / `error` / `warn` / `ignore` | DOCS `settings/cli.md#pmonfail` |

### Ways to get 12

| Way | Changes global install? | Notes / source |
|---|---|---|
| **Corepack + pin (this machine)** | **No** | Corepack ≥ the version here reads `devEngines.packageManager` (object form) as well as `packageManager`; they must agree if both are set (local `corepack@0.35.0`, `dist/lib/corepack.cjs`). For pnpm ≥ 11 Corepack runs `./bin/pnpm.mjs`. In 12 that wrapper downloads the native binary on first use through the bundled `get-pnpm`, which verifies it, and keeps it next to the wrapper (comments in `package/bin/pnpm.mjs` and `install.js` of the 12.18.0 tarball). Cost: a Node.js shim on every call; pnpm docs say "Do not use Corepack" for CI (DOCS `continuous-integration.md`). |
| `pnpm self-update <ver>` | Under Corepack, no: it "leaves the global pnpm alone. In a project that pins pnpm, it still updates the pin. Outside such a project, it fails." | DOCS `cli/self-update.md`, v11 docs same text: https://github.com/pnpm/pnpm.io/blob/main/versioned_docs/version-11.x/cli/self-update.md. 11.10+ can switch to 12. It ignores the project's `minimumReleaseAge`/`trustPolicy` and uses the built-in default (1440), global config, `PNPM_CONFIG_*` or flags. |
| `pnpm with <ver> <cmd>` | No | Fails under Corepack (`ERR_PNPM_CANT_USE_WITH_IN_COREPACK`). DOCS `cli/with.md` |
| Standalone script `curl -fsSL https://get.pnpm.io/install.sh \| env PNPM_VERSION=12.17.0 sh -` | Yes (`PNPM_HOME`) | DOCS `installation.md`; Corepack's shim would have to be disabled first [inference] |
| `npm install -g pnpm@12.17.0` | Yes | Package has `preinstall`/`postinstall` scripts (`node install.js`) that link the native binary; when scripts are blocked it falls back to the Node wrapper (REG, tarball `install.js`) |

### What the owner runs here (per project, no global change)

The project has no `package.json` yet. [inference, built from the sources above]
1. Create `package.json` with the `devEngines` block from §5 (`"version": "12.17.0"`). No command is needed to write the pin.
2. In the project directory: `pnpm --version` → Corepack fetches `pnpm@12.17.0`, the wrapper downloads `@pnpm/exe.linux-x64`, and it prints `12.17.0`. Outside the project it is still `11.25.0`.
3. `pnpm install` writes `pnpm-lock.yaml`, including `packageManagerDependencies`.
4. To move up later (e.g. 12.18.0 after 2026-11-12 01:00 UTC): `pnpm self-update 12.18.0` in the project. Under Corepack it only rewrites the pin.

Caveats:
- **[unconfirmed]** whether Corepack prompts before the first download (`COREPACK_ENABLE_DOWNLOAD_PROMPT`) or auto-adds a `packageManager` field. Not checked against Corepack docs.
- Local Corepack 0.35.0 declares `engines.node: ^22.22.2 || ^24.15.0 || >=26.0.0`, which **excludes Node 25**. It still runs today.
- Node 25 reached end of life on 2026-06-01 (https://raw.githubusercontent.com/nodejs/Release/main/schedule.json).
- **[unconfirmed]** whether an exact pin younger than `minimumReleaseAge` is refused when switching. Docs only state the rule for recording a range. Hence 12.17.0.

## 3. Settings for pnpm 12

File rule is unchanged from 11. "Only auth, registry, TLS, proxy, and `local-address` settings are read from `.npmrc`"; everything else goes in `pnpm-workspace.yaml` or global `config.yaml` (DOCS `settings.md`).

**New in 12:** an unknown key in `pnpm-workspace.yaml` **fails** with `ERR_PNPM_UNRECOGNIZED_WORKSPACE_SETTINGS` when the project pins a pnpm version the running pnpm satisfies (DOCS `migration-v11.md`). Typos no longer pass silently.

File = `pnpm-workspace.yaml` unless noted. DR = DOCS `settings/dependency-resolution.md`, B = `settings/build.md`, C = `settings/cli.md`, O = `settings/other.md`, S = `settings/store.md`.

| Key | v12 default | Recommended (owner's choices) | Src |
|---|---|---|---|

| `minimumReleaseAgeStrict` | `true` if `minimumReleaseAge` set explicitly, else `false` | implied `true`; may be written out | DR; CL 12.3.0 (v11 docs already describe the same default) |
| `minimumReleaseAgeExclude` | undefined | `[]`; names, patterns or `pkg@ver \|\| ver` only for urgent fixes. `pnpm audit --fix` auto-adds patched versions here | DR, DOCS `cli/audit.md` |

Notes on `pnx`:
- Outside a project only global config and defaults apply [inference].
- The executed package's own build scripts run by default. Its dependencies' scripts are prompted, or skipped without a TTY; `--allow-build` opts them in.
- In 12, `pnx node@…` / `pnx yarn@…` provision the real tool.
- `pnx` does not use the global virtual store.

## 4. Changes from 11 to 12

There is no codemod; config, lockfile and store are compatible (DOCS `migration-v11.md`). Behaviour changes, all from `migration-v11.md` unless noted:

| Change | Action |
|---|---|
| Unknown `pnpm-workspace.yaml` keys are an **error** when pinned; `confirmModulesPurge` rejected | remove or fix keys |
| Boolean flag + separate value rejected (`--frozen-lockfile false`) | `--no-frozen-lockfile` |
| `install --resolution-only` removed | `pnpm peers check` (blog) |
| GitHub/GitLab/Bitbucket git deps always HTTPS; no SSH URL in the lockfile | machine-level `insteadOf` |
| pnpmfile: `importPackage` not run; `filterLog` ignored | `packageImportMethod`, `loglevel` |
| `engineStrict` covers optional subtrees reached via regular edges; with `--no-runtime`/`runtime: false`, `engines.node` is checked against the active Node | — |
| `pnpm add yarn`, `add -g node`, `pnx node` provision the tool, not the npm package | use `yarn@npm:yarn@1.22.22` for the npm package |
| Global Node follows the project pin (`globalShims` default on) | `globalShims: false` globally, or `PNPM_SHIM_BYPASS=1` |
| `setup` / `self-update` / global installs under `sudo` fail (`ERR_PNPM_SUDO_NOT_SUPPORTED`) | run as your user |
| TLS: OS cert store (fallback: bundled Mozilla) instead of Node's bundle | `ca` / `cafile` if needed |
| `maxsockets` no longer defaults to 50 (direct connections) | set if the registry limits |
| `shellEmulator` uses pnpm's own shell (some `${…}` forms literal) | — |
| `scriptsPrependNodePath` ignored (no longer documented since 12.15) | — |
| `packageImportMethod: auto` on Linux: hardlink before clone | `clone` on btrfs if wanted |
| Deterministic cycle breaking; one-time lockfile diff on first re-resolve | commit the diff |
| `pnpm dlx` / `pnx` don't use the global virtual store | — |
| `pnpm pack-app` embeds Node 25.5.0 by default | `--runtime` |
| `--frozen-store` has no Node requirement | — |
| Default store falls back to `<project>/node_modules/.pnpm-store` when no parent dir accepts hardlinks; `pnpm init` pins npm `latest` | release notes https://github.com/pnpm/pnpm/releases/tag/v12.0.0 |
| Compatibility DB: statically-detected entries removed | same |

Changes inside 12.x worth knowing (CL):
- 12.3.0 `minimumReleaseAgeStrict` defaults to true when explicit.
- 12.3.0 `remove` / `update` accept the trust flags.
- 12.7.0 `trustPolicy` picks the newest non-downgraded version.
- 12.8.2 `childConcurrency` default fixed to 5.
- 12.9.0 `devEngines` range keeps the locked version.
- 12.11.0 `permissions` and agent skills.
- 12.16.0 `add` / `remove` / `update` fail instead of silently reinstalling when `node_modules` doesn't match the settings (`ERR_PNPM_MODULES_BREAKING_CHANGE` etc.).

Not renamed in 11→12: `allowBuilds`, `pmOnFail`, `audit.*`, `registries`, `trustLockfile` all carry over. Version labels differ, though: the 12 docs label `trustPolicyExcludePrune` "Added in v12.4.0" and `audit.ignorePrune` "v12.0.0", while the earlier report found them in 11.27 / 11.25. They are back-ported features with separate labels per line [inference].
